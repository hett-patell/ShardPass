ShardPass uses the maintained tokenizer and token parser directly so its protected `parseNumber(numberText)` API validates the original numeric lexeme before conversion: only unsigned canonical integer grammar is accepted, then `BigInt` enforces `0..Number.MAX_SAFE_INTEGER`, and only then is a Number produced. Project 1 Task 9.5 introduces exact-pinned `jsqr@1.4.0` (Apache-2.0) from the official `cozmo/jsQR` repository. The package was last released on 2021-04-24 and is therefore treated as an older, narrowly contained decoder rather than a generally trusted image stack. It has zero runtime dependencies, includes TypeScript declarations, runs in Chrome 110-compatible JavaScript over caller-supplied RGBA, and contains no network access, dynamic evaluation, WebAssembly, native code, or runtime asset loading. Registry integrity is pinned in `pnpm-lock.yaml`. It is bundled locally into a dedicated single-use module Worker; the vault page enforces an 8 MiB encoded-byte cap before read/transfer. `jsQR` returns one deterministic result, not an enumeration: the Worker returns its first decodable symbol only. Images containing multiple symbols are unsupported and are not guaranteed to be rejected; the safe preview and explicit confirmation apply to the one returned candidate. The package's age is accepted only with strict isolation, fixed timeout/abort/termination, schema validation, cleanup, build scan, and reproducibility evidence. No claim of a third-party security audit is made.

Task 9.5 correction round 2 retains only exact `image-dimensions@2.5.1` (MIT, zero dependencies, Sindre Sorhus's maintained `sindresorhus/image-dimensions`, released 2026-05-12) for a bounded PNG signature and first-IHDR dimension read before invoking the browser decoder. It does not scan later chunks or establish that the first IHDR is unique or authoritative. Review proved that `png-validator@2.0.0` does not provide the previously documented complete PNG contract: it accepts duplicate IHDR, skips CRC checks for unknown ancillary chunks, does not enforce exact IHDR/IEND lengths or all required chunk ordering, and uses module-global mutable parser state. `is-apng@1.2.0` explicitly documents quick detection rather than integrity validation. Both were removed from the catalog, package, and lockfile, and no manual PNG wire/chunk parser replaced them. Searches found no exact-pinnable maintained browser library exposing a full non-pixel PNG structural contract without either decoding pixels, incomplete checks, Node-oriented machinery, or a broader unsuitable dependency surface.

The maintained boundary is therefore the browser's native WebCodecs `ImageDecoder`, available in dedicated workers since Chrome 94 and therefore within minimum Chrome 110. Input remains static PNG only. `image-dimensions` rejects non-PNG and bounds the dimensions declared by the first IHDR to 4,096 per axis and an overflow-safe 16,777,216 pixels before native decoder construction. This is not a strict bound on native decoder allocation or processing: `ImageDecoder` may parse, process, or allocate during construction, `completed`, or `tracks.ready`, before the explicit `decode()` call. A PNG with duplicate or conflicting IHDR data could therefore cause the native decoder to act on larger dimensions before ShardPass receives a frame and rejects the later coded/display mismatch. The 8 MiB encoded-byte cap, dedicated Worker isolation, ten-second termination, browser-native limits, and resource closure mitigate this residual exposure but do not prove a hard native-memory or decompression bound.

With the complete bounded `Uint8Array`, the Worker awaits native buffering and track readiness, requires one selected non-animated track with exactly one frame, decodes only frame zero with `completeFramesOnly`, requires a complete result, and requires coded/display dimensions to equal first-IHDR preflight dimensions. Only after those checks does ShardPass allocate `OffscreenCanvas` and JavaScript-visible RGBA; that application-owned canvas/RGBA allocation is bounded by the checked dimensions. Native rejection covers malformed encoded structures, but ShardPass does not claim independent CRC/chunk-order conformance: the browser image decoder remains an attack surface and format-acceptance authority. JPEG, WebP, GIF, SVG, APNG/multiframe PNG, unsupported browsers, and decoder disagreement fail with fixed errors; there is no `createImageBitmap` or main-thread pixel fallback. `ImageDecoder`, `VideoFrame`, and `OffscreenCanvas` require no package, network, eval, WASM, or CSP change.

Zod is introduced by the messaging boundary for strict runtime schemas. Messaging imports the exact-pinned package's `zod/mini` entry and uses its strict-object, literal, discriminated-union, integer, nonnegative, minimum-length, and optional APIs. This preserves Task 3 runtime rejection behavior while tree-shaking the full Zod object JIT and its `Function` constructor paths from production artifacts. The production executable scanner is the final enforcement boundary and rejects dynamic code generation regardless of dependency source. It uses exact-pinned Acorn 8.17.0 (MIT), eslint-scope 9.1.2 (BSD-2-Clause), and parse5 8.0.1 (MIT), all mature packages whose reviewed releases predate the 24-hour minimum age. Acorn provides ECMAScript module ASTs; eslint-scope resolves lexical scopes and binding identities across programs, functions, blocks, catch clauses, loops, classes, and imports before the bounded alias policy evaluates code; parse5 provides structural HTML nodes and decoded attributes for inline-code and executable-resource policy. The policy is intentionally not comprehensive arbitrary-JavaScript taint analysis. It is a bounded, fail-closed syntactic policy: any reference to unshadowed global `eval` or `Function` as a value, call target, or constructor is rejected at its dangerous source; statically recognizable `eval`/`Function` access through unshadowed `globalThis` or a binding initialized from a `globalThis` alias is likewise rejected. Provenance analysis is separate from violation reporting. After lexical scope resolution, declarations and assignments are repeatedly collected to a fixed point before a clean violation pass begins. Each binding occupies a finite bit-set lattice over `{ eval, Function, globalThis }`; joins only add bits, never remove them. The convergence guard permits at most three bit additions per binding plus one confirming pass, so textual order and alias chains across nested functions cannot affect results and nontermination fails closed as a scope-analysis error. Later assignments, branch order, loops, try/catch/finally, and nested function traversal therefore cannot clear or introduce control-flow-dependent safety. Computed nonliteral member access through `globalThis` provenance is rejected conservatively. Object-pattern declarations and assignment destructuring from a `globalThis`-provenance source also reject every non-static computed key; static computed `eval`/`Function` keys receive normal dynamic-code provenance, while other static keys and computed destructuring from ordinary local objects remain allowed. Lexically resolved imported, local, block, function, class, loop, and catch bindings named `eval` or `Function` remain allowed. This deliberately accepts conservative false positives after a binding has ever acquired relevant global provenance; it does not claim completeness for arbitrary dynamic-property construction or whole-program taint. Parse errors, computed dynamic imports, and relevant computed global access fail closed. The same lexical resolution rejects remote or computed destinations at unshadowed global `fetch`, `XMLHttpRequest.open`, `WebSocket`, `EventSource`, and `navigator.sendBeacon`; it tracks direct/aliased `Image` and recognizable `img`/`audio`/`video`/`source`/`track` bindings for `src` and `setAttribute`. Shadowed globals and static packaged relative/root-local URLs remain allowed. HTML scanning rejects remote/protocol-relative image, media, track, icon, preload, prefetch, and manifest resources. This remains a bounded recognizable-sink policy rather than arbitrary whole-program network taint analysis. ## Project 1 Task 12 Ente OTP sync

ShardPass pins the Ente compatibility contract to `ente-io/ente@c69dcf66704ad7ec1f95e32920455be429a566ef` and permits only `https://api.ente.io`. Synchronization is OTP-only (TOTP, HOTP, Steam), fixed-origin, background-owned, and active only while connected and unlocked on connect/restart/unlock/manual/exact 15-minute alarm triggers. The extension CSP is exactly `script-src 'self' 'wasm-unsafe-eval'; object-src 'self'; connect-src 'self' https://api.ente.io; img-src 'self' data:; media-src 'self'; font-src 'self'; style-src 'self'`; `'unsafe-eval'`, custom servers, redirects, cookies, telemetry, WebSockets, and remote executable resources remain forbidden.

Reusable credentials, Auth-key material, mappings, bases, pending operations, uncertainty, and conflicts are confined to authenticated encrypted vault generation metadata. The full-vault UI receives bounded counts, times, masked email, and opaque expiring capabilities only; popup is summary-only; content scripts have no Ente authority. Memory cleanup is best effort and does not substitute for logical invalidation on lock, restart, replacement, disconnect, or stale async ownership. Disconnect is local-only: it does not delete local or remote OTP records, cannot undo a possibly dispatched request, and performs no network request. The API has no cross-device transactional CAS; snapshot reconciliation and explicit conflicts contain concurrent/uncertain writes but cannot provide impossible atomicity.

Production uses exact `libsodium-wrappers-sumo@0.8.4` with forced `libsodium-sumo@0.8.0` (ISC) and the Phase 1-selected exact SRP dependency. This is not an independent libsodium integration audit. Any protocol, dependency, CSP, WASM graph, endpoint, scheduler, or origin upgrade requires the complete Task 12 compatibility, integrity, packaged-browser, security, and license review again.
