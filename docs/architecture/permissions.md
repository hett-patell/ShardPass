# Current Project 1 manifest permissions

**Verified:** 2026-09-16 against `apps/extension/src/manifest.ts`, `tests/security/manifest.test.ts`, current output assertions, and Task 13 policy

This document describes the maintainable current Project 1 build, not the preserved ShardPass 1.2.1 root manifest. Implemented OTP, clipboard copy through the page Clipboard API, explicit click-to-fill, login and data fill, passkeys, import/migration, backup, fixed-origin OTP-only Ente sync, k-anonymous breach lookups, and DuckDuckGo email aliases are the reasons for the grants below; nothing here is held for a future feature.

Task 13 changes no extension permission. Release tooling network modes are process/container policy, not manifest grants: `bootstrap` reaches one registry, `offline` reaches none, `mock` reaches loopback only, and `audit` reaches the exact registry audit endpoint. The same frozen candidate manifest and CSP are checked before a canonical `PASS-PROJECT1-RELEASE`; Node 24/Chromium 151 development-only output cannot waive a mismatch or replace actual Chrome 110 and signed external review.

## Current authority

The built manifest grants seven API permissions — `storage`, `unlimitedStorage`, `alarms`, `idle`, `activeTab`, `contextMenus`, and `favicon` — and two host permissions, `https://api.ente.io/*` and `https://quack.duckduckgo.com/*`. There is no `optional_host_permissions` and no `externally_connectable`.

## Network authority

The extension reaches exactly three origins, all from the background service worker:

- `https://api.ente.io` — OTP-only sync, active only while connected and unlocked. Host permission and `connect-src`.
- `https://quack.duckduckgo.com` — one POST to mint an Email Protection alias when the person asks for one. Host permission and `connect-src`.
- `https://api.pwnedpasswords.com` — the padded k-anonymity range endpoint, which sends only the first five characters of a password's SHA-1 and never the password. It needs no host permission because the endpoint serves permissive CORS headers, so `connect-src` is the whole grant.

Nothing else is reachable. `<all_urls>` as a content-script match is not a `host_permissions` entry and does not authorize extension pages or the service worker to issue requests to matched sites.

## The content script is not inert

Earlier project phases shipped a deliberately inert content entry. It is not inert now. `apps/extension/src/content/main.tsx` starts four controllers in every matched frame and disposes them on `pagehide`:

- the OTP fill controller — bounded field discovery, one focused-field trigger, a metadata-only picker, and one explicitly selected five-second field-bound release;
- the login fill controller — username/password suggestions, the save-login offer, and the explicit fill selection;
- the data fill controller — card and identity fill, gated on a grant issued by a trusted extension page;
- the passkey bridge — the isolated-world half of WebAuthn, paired with the one `MAIN`-world page script.

The page and the content script both remain untrusted. Suggestions carry bounded display metadata; seeds, full records, passwords, HOTP counters, notes, keys, and session epochs stay background-only. The controllers never submit a form, press Enter, click page controls, or persist page observations.

## Explicitly absent

- no `clipboardRead` and no `clipboardWrite`; copying goes through the page Clipboard API on an explicit user gesture in a trusted extension page;
- no camera permission and no live capture; QR import accepts only browser-provided local Blob/File image bytes in the trusted vault page and decodes native-accepted, one-track/one-frame PNG locally in a dedicated module Worker; browser-native decoding is the acceptance boundary, not independent structural or CRC validation;
- no `offscreen`; Argon2, KeePass, strength estimation, and bounded QR decoding run in dedicated Workers owned by trusted extension pages, without an offscreen document;
- no `tabs`; `activeTab` covers the one tab the person is acting on, and reading this extension's own pages back needs no permission at all;
- no `notifications`, `downloads`, `identity`, `scripting`, `webRequest`, `cookies`, `management`, `debugger`, or native messaging; export uses a direct user-gesture `<a download>` with a page-owned Blob object URL, revokes and replaces that URL on its bounded lifecycle, and never calls the downloads API;
- no `externally_connectable`, so websites and external extensions are not invited to message this extension;
- no `optional_permissions` and no `optional_host_permissions`; the grant set is what the store listing shows at install time;
- no web-accessible picker or API resource authored by us. CRXJS lists the generated content entry and the passkey page script as build resources; this does not make a callable secret API.

Backup does not widen authority: files are selected only through the trusted full-vault page's browser file control, are size-bounded before reading, and are processed locally. A Blob object URL is a page-local download mechanism rather than runtime network or host authority.

## Why `<all_urls>` is retained

Reliable field discovery, click-to-fill, the save-login offer, and passkeys across user-selected sites all require matching those sites, and a content script cannot discover fields on a site it does not match. An allowlist workflow would move the same reach behind a per-site prompt rather than remove it, and would break the passkey bridge, which must be present at `document_start` before the page calls `navigator.credentials`.

The chosen trade-off is transparent rather than least possible reach: match broadly, keep every secret release authorized in the background from browser-owned metadata, hold the network grant to three named origins, and treat any change to content behaviour as a security-reviewed change. User-facing store disclosures must accurately describe the resulting page access.

## Future permission gate

Future needs are not current grants:

- Additional alarm or idle behaviour requires lock-policy tests; current use is the auto-lock, the system lock, and the fixed Ente sync interval.
- Ente access must stay OTP-specific and allowlist only documented endpoints; it must not become generic password sync.
- No generalized sync host is pre-authorized before its separately approved project.
- Any new host, optional host, frame expansion, `MAIN`-world script, or API permission requires source and built-manifest assertions, updated runtime boundaries/threat model/store disclosure, and browser evidence.

## Project 1 Task 12 Ente OTP sync

ShardPass pins the Ente compatibility contract to `ente-io/ente@c69dcf66704ad7ec1f95e32920455be429a566ef` and permits only `https://api.ente.io`. Synchronization is OTP-only (TOTP, HOTP, Steam), fixed-origin, background-owned, and active only while connected and unlocked on connect/restart/unlock/manual/exact 15-minute alarm triggers. `'unsafe-eval'`, custom servers, redirects, cookies, telemetry, WebSockets, and remote executable resources remain forbidden.

Reusable credentials, Auth-key material, mappings, bases, pending operations, uncertainty, and conflicts are confined to authenticated encrypted vault generation metadata. The full-vault UI receives bounded counts, times, masked email, and opaque expiring capabilities only; popup is summary-only; content scripts have no Ente authority. Memory cleanup is best effort and does not substitute for logical invalidation on lock, restart, replacement, disconnect, or stale async ownership. Disconnect is local-only: it does not delete local or remote OTP records, cannot undo a possibly dispatched request, and performs no network request. The API has no cross-device transactional CAS; snapshot reconciliation and explicit conflicts contain concurrent/uncertain writes but cannot provide impossible atomicity.

Production uses exact `libsodium-wrappers-sumo@0.8.4` with forced `libsodium-sumo@0.8.0` (ISC) and the Phase 1-selected exact SRP dependency. This is not an independent libsodium integration audit. Any protocol, dependency, CSP, WASM graph, endpoint, scheduler, or origin upgrade requires the complete Task 12 compatibility, integrity, packaged-browser, security, and license review again.
